## 一、产品定位分析

### 1. 这个项目解决什么现实问题？

国际商务沟通中，"表达风险"真实存在且代价高昂：

- **语言风险**：语法错误、中式英语（Chinglish）、术语误用，轻则显得不专业，重则造成合同与价格上的理解偏差（如"quotation is too expensive"这类搭配错误、数字/日期表达歧义）。
- **商务礼仪风险**：称呼不当（直呼客户名字、漏用头衔）、请求语气生硬（"You must send us..."）、缺少寒暄与致谢、回复时效承诺含糊——直接损害职业形象与合作意愿。
- **跨文化风险**：不同文化对"直接 vs 委婉""等级 vs 平等""个人 vs 关系""时间观念"的期望完全不同。对日本客户直白拒绝、对阿拉伯客户强调截止日期、对欧美客户过度使用敬语，都可能引发误解甚至冒犯。

**核心问题**：现有工具（翻译软件、语法检查、通用 AI 写作助手）只解决"对不对/通不通"，**没有工具系统性地回答"失不失礼、合不合文化、伤不伤关系"**。学生和职场新人缺乏跨文化专家的贴身把关，出错后往往不自知。CrossBridge 解决的就是这个"专业盲区"。

### 2. 目标用户是谁？

| 用户群 | 典型场景 | 痛点 | 本项目价值 |
|---|---|---|---|
| **外贸新人** | 给海外客户写开发信、报价、催款、处理投诉 | 怕得罪客户、不知邮件怎么措辞得体、被客户"已读不回" | 发送前风险体检：指出冒犯点并给出可直接复用的得体表达 |
| **商务英语专业学生** | 课堂邮件写作、模拟谈判、国际商务案例学习 | 老师批改反馈有限，缺少"为什么错、错在文化还是语言"的归因 | 学习辅助：每个问题附文化与语言双重解释，形成"案例学习库" |
| **国际交流人员**（外事、翻译、外企员工） | 国际会议发言、跨部门沟通、对外邮件 | 会议发言过直得罪人、与不同文化同事协作易生摩擦 | 会前/发送前快速自查，降低沟通摩擦 |
| **有跨文化需求的普通用户** | 与海外客户、房东、朋友、婚恋对象沟通 | 不敢开口、担心失礼、闹文化笑话 | 低门槛的"文化沟通教练"，教你说得得体、懂对方文化 |

> 比赛展示聚焦优先级：**外贸新人 > 商务英语学生 > 国际交流人员 > 普通用户**。演示剧本围绕前两类设计，最容易打动评委（贴近真实商业场景、有故事感）。

### 3. 为什么属于"新文科实践创新"，而不是普通 AI 工具？

判断标准不是"用了 AI"，而是"AI 与学科知识如何结合、解决了什么学科性问题"。本项目满足以下条件：

1. **学科交叉驱动**：项目同时调用商务英语（语用学、商务信函规范）、跨文化交际学（霍尔高低语境理论、霍夫斯泰德文化维度、面子理论）、管理学（商务礼仪与关系维护）三个学科的知识体系。**AI 是执行引擎，学科知识才是判断标准。**
2. **知识库是自建的专业资产**：100 条专家标注案例库、五维评价模型、文化知识库均由团队（商务英语背景学生 + 指导教师）用学科方法构建，不是从网上抓的通用数据。这是"文科实践"的具体成果物。
3. **解决的是真实的社会问题**：中国外贸从业者超千万，"出海"时代下跨文化沟通失误频发（曾有外贸公司因邮件措辞失礼丢单的真实案例）。项目回应了国家"国际传播能力建设""文化走出去"的时代命题。
4. **实践闭环完整**：从理论（跨文化理论）→ 知识工程（案例库建设）→ 产品化（AI 应用）→ 验证（用户测试），是一条完整的新文科"学—研—产"链路。

> 一句话答辩话术：**"普通的 AI 工具是通用模型随便回答；我们的 AI 背后是一套由商务英语与跨文化交际学科知识构建的专业评价体系，AI 负责执行，学科负责标准。"**

### 4. 商务英语专业在项目中的核心价值是什么？

商务英语专业不是"提供素材"的边缘角色，而是项目的**大脑与护城河**：

- **定义评价标准**：五维评分模型中的"语言准确性、商务礼貌、文化适配"等维度的评分锚点（什么样的表达算 10 分、什么样的算 2 分），必须由懂商务语用学的专业人士制定，AI 无法凭空生成。
- **构建案例库**：100 条案例的"问题分析、推荐表达、文化解释"需要语言学与跨文化交际的专业功底才能写好——这是模型之外、别人抄不走的资产。
- **校准 AI 输出**：AI 改写的表达是否真的得体、是否保留了商务意图（催款 vs 催货语气不同），需要专业人工审核校准。
- **面向比赛讲述学科故事**：答辩与展示中，团队可以展示"我们如何把课堂上学的高/低语境理论变成评分维度和案例"，这是典型的文科成果转化。

> 项目定位结论：**这是一款"商务英语专业知识产品化"的工具，AI 是放大器，专业是内核。**

## 二、MVP 最小可行产品设计

### 2.1 MVP 核心理念（一句话）

> **用户输入一句国际交流文本 → AI 六步分析 → 生成一份专业风险报告。**

MVP 只做一个闭环：**一条文本进，一份报告出。** 不做账号体系、不做批量、不做社交，把单次体验打磨到"让评委 3 分钟看懂价值"。

### 2.2 核心功能（第一版必须实现）

| # | 功能 | 说明 | 优先级 |
|---|---|---|---|
| 1 | 文本输入 | 文本框输入一句/一段国际交流文本（支持中英混合输入，如"我们下周一给您发样品"），可自选沟通场景（邮件/谈判/会议/客户沟通/日常交流） | P0 |
| 2 | 场景识别 | AI 自动识别沟通场景、渠道与双方关系（若用户手动选了场景则以用户选择为准） | P0 |
| 3 | 六维分析引擎 | 语言分析、商务礼仪分析、文化风险分析三条线并行，输出结构化问题列表 | P0 |
| 4 | 五维评分 + 风险等级 | 输出 Language Accuracy / Business Politeness / Cultural Adaptability / Communication Clarity / Relationship Friendliness 五维得分、加权总分、四档风险等级（绿/黄/橙/红） | P0 |
| 5 | 专业风险报告展示 | 前端报告页：总分与雷达图、每条问题的"原文 → 问题分析 → 优化表达 → 文化解释"对照卡片、风险等级标识 | P0 |
| 6 | 案例对照（亮点） | 报告末尾附 1–2 条与当前场景相关的案例库真实案例，展示"专业内核"（如"历史案例：曾有外贸新人对日本客户直接说 No，导致订单流失"） | P0 |
| 7 | 演示兜底 | 内置 3 个演示剧本（邮件/谈判/会议），一键填入，保证比赛现场演示不冷场 | P0 |

### 2.3 非核心功能（第一版暂不开发）

| 暂缓功能 | 原因 |
|---|---|
| 用户注册 / 登录 / 历史记录 | 增加复杂度且比赛不考核；留到阶段 2 可选 |
| 批量/文件导入分析（Excel、邮件导入） | 超出 MVP 闭环 |
| 全文逐句高亮标注 | 好但费工，阶段 2 再做 |
| 多语言报告（日/韩/西语输出） | 成本高，MVP 只做中文界面 + 中英双语解释 |
| 付费、会员、商业化 | 比赛阶段完全不需要 |
| 移动端 App | 只做网页端，桌面/手机浏览器均可访问 |
| 实时聊天式交互 | 保持"输入→报告"的单次任务模式，交互更简单、演示更可控 |

### 2.4 MVP 用户流程（演示动线）

```
打开首页 → 选择演示剧本或手动输入文本 → 点击"开始分析"（约 3–8 秒）
→ 展示分析过程（分步状态：场景识别→语言→礼仪→文化→评分→建议）
→ 展示专业报告页（评分雷达图 + 风险等级 + 问题对照卡片 + 案例参考）
→ 一键"换一句再测" 或 "复制优化后表达"
```

## 三、产品功能架构

| 模块 | 功能 | 输入 | 输出 | 技术实现方式 |
|---|---|---|---|---|
| **模块1：文本输入模块** | 接收用户文本；提供演示剧本快捷填入；场景可选（邮件/谈判/会议/客户沟通/日常交流） | 用户输入文本（≤500 字）、可选场景标签 | 结构化请求体（text, scene?, channel?） | 前端 Vue3 表单 + 后端 Pydantic 校验 |
| **模块2：场景识别模块** | 识别沟通场景、渠道、双方关系、可能的文化语境；决定后续分析侧重点与案例检索范围 | 用户文本 + 可选场景标签 | 场景标签 JSON（scene / channel / relation / culture_hint） | LLM 结构化输出（JSON mode）+ 关键词规则辅助；结果用于查询案例库子集 |
| **模块3：跨文化风险分析模块**（核心） | 三条分析线并行：①语言分析（语法/词汇/术语/中式英语）②商务礼仪分析（称呼/请求语气/礼貌度/时效承诺）③文化风险分析（高低语境/直接性/等级观/面子/时间观/禁忌） | 用户文本 + 场景标签 | 问题列表：每条含 {位置, 类型, 严重度, 分析说明, 对应文化维度} | LLM 三次并行调用（或一次调用按结构化 schema 返回三段），提示词内嵌学科检查清单 |
| **模块4：评分模型模块** | 按五维模型逐维打分（每维 0–10 + 一句理由）→ 加权总分 → 映射四档风险等级 | 问题列表 + 用户文本 + 场景标签 | 结构化评分 JSON（五维分、总分、风险等级、等级说明） | LLM 评分 + 后端规则校验（分值范围、枚举合法性；非法则重试或按规则降级） |
| **模块5：优化建议生成模块** | 对每条问题生成：优化后表达（替换句）、为什么这样改（语言/礼仪/文化三重解释）、语气等级提示 | 问题列表 + 评分结果 | 优化建议列表（原文→优化→解释→标签） | LLM 生成 + 与案例库相似案例比对补充"历史案例参考" |
| **模块6：案例数据库模块** | 存储 100 条专家案例；按场景/文化维度检索；在报告中附带相关案例；作为少样本示例注入提示词 | 查询条件（场景、文化维度、关键词） | 匹配案例 JSON 列表 | `data/cross_culture_cases.json` 本地文件加载，程序内简单关键词/标签匹配（MVP 不引入向量库，阶段 2 可选接入 embedding 检索） |

**模块依赖关系（数据流）**：

```
模块1 → 模块2 → 模块3 ─┬→ 模块4 → 模块5
                        └→ 模块6（检索案例，供模块4/5参考并在报告展示）
```

## 四、AI 分析逻辑设计

### 4.1 总体工作流

```
用户输入文本
    ↓
[1] 场景识别
    ↓
[2] 语言分析 ──────┐
[3] 商务礼仪分析 ───┼─ 并行（互不依赖，可同时调用）
[4] 文化风险分析 ───┘
    ↓
[5] 五维评分 + 风险等级
    ↓
[6] 优化建议（逐条改写 + 三重解释）
    ↓
专业风险报告（前端渲染）
```

> 工程建议：步骤 2/3/4 三条分析线并行调用（节省时间、互不污染）；步骤 1 的结果同时用于缩小步骤 6 的案例检索范围。MVP 阶段也可合并为"1 次主调用 + 1 次评分调用"共 2 次 LLM 请求，控制延迟与成本。

### 4.2 每一步 AI 要完成的任务

| 步骤 | AI 任务 | 输入 | 输出 | 提示词要点（专业锚点） |
|---|---|---|---|---|
| **1 场景识别** | 判断沟通场景（商务邮件/商务谈判/国际会议/客户沟通/日常跨文化）、沟通渠道（邮件/即时消息/电话/面谈/会议发言）、双方关系（客户-供应商/上下级/平级同事）、可能的对方文化线索 | 用户文本 | 结构化 JSON：scene, channel, relation, culture_hint | 只输出分类标签，禁止发散；无法判断时给默认值"general" |
| **2 语言分析** | 检查：语法错误；词汇搭配不当；术语误用；拼写；语域不当（太口语/太僵硬）；中式英语痕迹；数字/日期/价格表达歧义 | 文本 + 场景标签 | 语言问题列表：{quotation, error_type, severity, explanation} | 附商务英语高频错误清单（如 "cost is expensive"、"for your reference please"）；每条必须给出"错在哪"的证据 |
| **3 商务礼仪分析** | 检查：称呼与头衔（Mr./Ms./Dr./职位头衔）；问候与寒暄；请求语气（是否命令式）；礼貌程度（please/could/would 层级）；时间承诺与回复时效表述；致谢与跟进用语 | 文本 + 场景标签 | 礼仪问题列表：{quotation, etiquette_type, severity, explanation} | 强调"商务邮件五步结构"（称呼-背景-请求-理由-致谢）与"请求语气阶梯"（You must → Please → Could you → Would you mind） |
| **4 文化风险分析** | 识别文化敏感点：高低语境差异（日韩高语境 vs 欧美低语境）；直接/委婉偏好；等级观念（对日韩/中东客户的头衔尊重）；面子文化（当众纠错/直接拒绝的伤害）；时间观（单时制 vs 多时制）；话题禁忌；礼物与社交规则 | 文本 + 场景标签 | 文化风险列表：{quotation, culture_dimension, affected_cultures, explanation} | 提示词内置理论框架：霍尔高低语境、霍夫斯泰德文化维度、面子理论；输出必须引用具体文化维度名称 |
| **5 五维评分** | 按五维模型逐维打分（0–10），每维给出评分依据一句话；计算加权总分；映射风险等级（绿/黄/橙/红）；给出总分一句话总评 | 文本 + 全部问题列表 | 评分 JSON：{scores: {la, bp, ca, cc, rf}, total, risk_level, summary} | 严格按评分锚点打分（见第五章）；输出必须是合法 JSON，分值 0–10 整数 |
| **6 优化建议** | 对每条问题生成替换表达（保持原商务意图不变，如催款仍是催款）；给出三重解释（语言层面为什么错 / 礼仪层面为何失礼 / 文化层面对方会怎么想）；语气提示（如需更温和/更坚定） | 问题列表 + 评分 + 检索到的相似案例 | 建议列表：{original, optimized, explanation_language, explanation_etiquette, explanation_culture} | 输出必须是"可直接复制使用"的整句替换，而非零散修改意见；引用案例库相似案例增强可信度 |

### 4.3 稳定性设计原则

- **全部结构化输出**：所有步骤强制 JSON 格式返回，后端用 schema 校验字段与枚举，非法输出自动重试 1 次，仍失败则使用规则兜底（默认值 + 提示用户）。
- **分步可控**：六步拆成独立小任务，任何一步失败不影响其他步骤结果展示，避免"一次大调用全盘失败"。
- **专业锚点注入**：把学科检查清单写进提示词（而非完全依赖模型自由发挥），保证"商务英语专业特色"稳定出现。

## 五、专业评价模型设计

### 5.1 模型名称与总览

**模型名称：跨文化商务沟通风险评价模型（Cross-Cultural Business Communication Risk Assessment Model, CCRM）**

| 维度 | 名称 | 权重 | 满分 | 考察什么 |
|---|---|---|---|---|
| 1 | Language Accuracy（语言准确性） | 3.0 | 30 | 语法、词汇搭配、术语、拼写、语域 |
| 2 | Business Politeness（商务礼貌程度） | 2.0 | 20 | 称呼、请求语气、敬语、寒暄致谢 |
| 3 | Cultural Adaptability（文化适配程度） | 2.0 | 20 | 高低语境、直接性、等级观、面子、时间观 |
| 4 | Communication Clarity（表达清晰程度） | 2.0 | 20 | 结构逻辑、要点明确、数据时间完整 |
| 5 | Relationship Friendliness（关系维护友好度） | 1.0 | 10 | 关系意识、后续跟进、长期合作导向 |
| | **综合** | **10.0** | **100** | **总分 = Σ(维度分 × 权重)** |

> 权重设计理由：语言准确性是基础分（3.0），但项目差异化在于礼仪与文化（各 2.0），清晰度 2.0，关系维护是加分项（1.0）——总分结构既能体现"专业体检"定位，又不会让文化维度喧宾夺主。

### 5.2 各维度评价标准（评分锚点，0–10 分）

| 分值 | Language Accuracy | Business Politeness | Cultural Adaptability | Communication Clarity | Relationship Friendliness |
|---|---|---|---|---|---|
| 10 | 无语法/拼写错误，词汇术语地道，语域恰当 | 称呼得体、请求委婉、敬语恰当、寒暄致谢完整 | 主动适配对方文化，表达在目标文化中自然无冲突 | 结构清晰、要点突出、时间/数据/要求完整明确 | 体现主动关系维护（感谢、跟进、邀约下次合作） |
| 7 | 少量小错，不影响理解 | 基本礼貌，个别语气略生硬 | 中性表达，无明显文化冲突 | 基本清晰，个别信息略模糊 | 有基本礼节性收尾，但无关系经营 |
| 4 | 多处语法错误/中式英语明显，需对方费力理解 | 语气生硬、有命令式表达、缺称呼或致谢 | 忽略文化差异，表达在目标文化中易生误解 | 重点模糊、关键信息缺失（时间/价格/要求） | 纯事务性沟通，无任何关系意识 |
| 1 | 错误频发，几乎无法顺畅理解 | 明显冒犯性表达（命令、指责、失礼称呼） | 触碰明显文化禁忌，可能造成冒犯 | 逻辑混乱，读者抓不住要点 | 冷漠、失礼或单方面施压 |

（7/4/1 为锚点分，中间分值由模型插值判断，每条评分必须附一句评分理由。）

### 5.3 综合评分与风险等级

- **总分** = 维度分(0–10) × 权重 之和，满分为 100。
- **风险等级映射**：

| 总分区间 | 风险等级 | 颜色 | 建议动作 |
|---|---|---|---|
| 85–100 | 低风险 | 🟢 绿 | 表达得体，可放心发送 |
| 70–84 | 中低风险 | 🟡 黄 | 建议小幅修改后再发送 |
| 50–69 | 中高风险 | 🟠 橙 | 建议修改后请同事复核再发送 |
| 0–49 | 高风险 | 🔴 红 | 不建议直接发送，需按建议全面重写 |

- **报告必含**：五维分数、总分、风险等级、一句话总评（如"整体表达礼貌得体，但直接否定对方报价在日韩文化中可能伤及面子，建议改用委婉让步句式"）。

### 5.4 评分输出结构（数据契约）

评分模块返回结构化 JSON（字段与枚举固定，后端强校验）：

```
scores: { language_accuracy: int(0-10), business_politeness: int(0-10),
          cultural_adaptability: int(0-10), communication_clarity: int(0-10),
          relationship_friendliness: int(0-10) }
total: int(0-100)
risk_level: "low" | "medium_low" | "medium_high" | "high"
summary: string        // 一句话总评
dimension_reasons: { 维度名: string }  // 每维一句评分依据
```

## 六、案例数据库设计

### 6.1 数据库结构：`cross_culture_cases.json`

采用单文件 JSON 存储（零部署、方便展示源码结构），字段设计如下：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✔ | 案例编号，如 `EM001`（场景前缀+序号） |
| `scenario` | string | ✔ | 场景分类，枚举：`business_email` / `business_negotiation` / `international_meeting` / `customer_communication` / `daily_cross_culture` |
| `sub_scene` | string | 建议 | 子场景，如"催款邮件""报价谈判""会议反驳发言" |
| `original_expression` | string | ✔ | 原表达（风险文本，可附简短上下文） |
| `problem_analysis` | string | ✔ | 问题分析：语言/礼仪/文化层面的具体问题与依据 |
| `risk_level` | string | ✔ | 风险等级：`low` / `medium_low` / `medium_high` / `high` |
| `recommended_expression` | string | ✔ | 推荐表达（可直接复用的优化版整句） |
| `culture_explanation` | string | ✔ | 文化解释：涉及的文化维度、对方文化视角、为何如此改 |
| `dimension_scores` | object | 建议 | 该案例的五维评分示例（供教学与校准 AI 输出用） |
| `target_culture` | string | 建议 | 关联文化/国家，如"Japan / 日本" |
| `tags` | array | 建议 | 标签：文化维度（`high_context`、`face` 等）+ 语言问题类型（`chinglish`、`tone` 等） |
| `source` | string | 建议 | 案例来源标注（自建/文献改编），体现学术规范 |

文件顶层结构：

```
{
  "version": "1.0",
  "description": "CrossBridge AI 跨文化商务沟通风险案例库",
  "total": 100,
  "categories": { "business_email": 20, "business_negotiation": 20,
                  "international_meeting": 20, "customer_communication": 20,
                  "daily_cross_culture": 20 },
  "cases": [ { ...如上字段的案例对象×100 } ]
}
```

### 6.2 100 条案例分类规划（5 大场景 × 20 条）

| 场景 | 子场景分布（各约 20 条） | 示例话题 |
|---|---|---|
| **1 商务邮件**（`business_email`） | 初次接触(3)、开发信(2)、询盘报价(3)、催款(3)、拒绝合作(2)、投诉与道歉(3)、确认与跟进(2)、会议邀请(2) | "We have not received your payment." 直接质问式催款；"Dear Sir" 性别与称呼失当 |
| **2 商务谈判**（`business_negotiation`） | 报价(3)、压价回应(3)、让步(3)、合同条款(3)、交货期(2)、付款方式(2)、分歧处理(2)、破裂收尾(2) | 对日方直接说 "Your price is unacceptable."；"We must sign today." 时间压迫式收尾 |
| **3 国际会议**（`international_meeting`） | 自我介绍(2)、发言开场(3)、提问(3)、反驳(3)、打断与插话(2)、总结陈词(3)、远程会议(2)、会后跟进(2) | 当众说 "You are wrong."；打断发言人 "Wait, let me talk." |
| **4 客户沟通**（`customer_communication`） | 需求确认(3)、进度汇报(3)、延误通知(3)、质量问题(3)、售后(3)、节日问候(2)、上门拜访(3) | "The delay is not our fault." 责任推诿；对阿拉伯客户用压缩交期承诺 |
| **5 日常跨文化交流**（`daily_cross_culture`） | 初次见面(3)、交换名片(2)、餐桌礼仪(3)、送礼(3)、称呼(3)、时间观念(3)、禁忌话题(3) | 对欧美同事问 "How much do you earn?"；单手递名片给日方客户 |

> 每条案例的质量标准：**真实可感**（源自外贸实务、教材语料、导师经验改编）、**分析专业**（语言+礼仪+文化三重归因）、**推荐可用**（整句可复制）、**来源可追溯**（自建/文献改编标注），避免直接复制受版权保护的邮件模板原文。

### 6.3 案例库在 AI 流程中的三重作用

1. **少样本注入**：把与当前场景匹配的 2–3 条案例写进提示词，让模型"照着专业案例的水准分析"。
2. **报告附案例**：报告中展示 1–2 条相关历史案例，向评委直观展示"专业内核与积累"。
3. **评分校准**：`dimension_scores` 可作为标准答案，用于阶段 2 校准模型评分（对比 AI 评分与专家评分）。

## 七、技术方案设计

### 7.1 设计原则

- **低成本**：首选 API 单次分析成本约 0.01 元级；全部框架与模型选开源免费方案；演示全程成本可控制在个位数元以内。
- **可运行**：技术栈成熟、资料多、出错好排查，团队成员（非计算机专业）两三天可上手。
- **方便展示**：浏览器即开即用；内置演示剧本；本地模型兜底保证比赛现场断网也能演示。

### 7.2 技术栈推荐

| 层 | 推荐方案 | 备选方案 | 选型理由 |
|---|---|---|---|
| **前端** | **Vue 3 + Vite + Element Plus**；图表用 **ECharts**（雷达图） | Streamlit（若前端经验薄弱，可先用它快速出原型） | 组件成熟、中文文档全、MIT 协议；雷达图是报告页核心视觉 |
| **后端** | **Python + FastAPI** | Flask | 类型校验（Pydantic）与 LLM 结构化输出天然契合；自动生成接口文档方便展示 |
| **数据库/数据** | **SQLite + 本地 JSON**（案例库 `cross_culture_cases.json` 直接读文件） | 无（MVP 不引入 MySQL/PostgreSQL） | 零配置、可把数据文件直接放进 GitHub 展示 |
| **AI 调用** | **DeepSeek 开放平台 API**（OpenAI 兼容接口） | ① 硅基流动 SiliconFlow 免费模型（Qwen2.5-7B 等，免费额度演示够用）② Ollama 本地部署 Qwen3 小模型（断网兜底） | 三层可切换（见 7.3），代码层只改一个 provider 配置 |

### 7.3 AI 调用三层策略（关键设计）

```
第一层（默认）：DeepSeek API（deepseek-chat）
   费用约 1–2 元/百万 tokens，单次报告约 2000 tokens ≈ 0.01 元；无需显卡、稳定快速
        ↓ 无额度 / 限流 / 现场断网时切换
第二层：硅基流动 SiliconFlow（免费模型，如 Qwen2.5-7B-Instruct / GLM-4-9B）
   免费额度 + 同接口格式，几乎零成本；效果略逊，但演示文本短，足够
        ↓ 完全离线 / 断网演示兜底
第三层：Ollama 本地部署（qwen3:8b 等小模型，MIT/开源协议）
   完全免费、离线可用、无网络依赖；笔记本可跑 7B 量化版
```

> 统一封装：后端写一个 `LLMProvider` 抽象层，三个 provider 均兼容 OpenAI 接口格式，通过 `config.py` 一个开关切换——这是"低成本 + 可运行 + 不怕现场事故"的工程关键。

### 7.4 关键技术点

- **结构化输出**：所有 LLM 调用启用 JSON 输出模式，后端 Pydantic 模型强校验，保证评分/问题列表字段合法可渲染。
- **提示词模板化**：`data/prompts/` 下存放各步骤提示词模板（含学科检查清单），便于迭代与展示"专业内核"。
- **延迟控制**：三条分析线并行；总请求控制在 2–3 次；前端展示分步进度动画（3–8 秒等待期间"有戏看"）。
- **安全与合规**：API Key 只放后端环境变量，不进前端；演示避免输入真实客户敏感信息（提示词与 README 中声明数据仅用于演示）。

## 九、开发路线规划

### 阶段 1：MVP 开发（建议 2–3 周）

- **目标**：跑通"输入文本 → AI 六步分析 → 专业风险报告"完整闭环。
- **完成内容**：
  - 后端：FastAPI 骨架 + DeepSeek API 接入 + 六步分析服务（先实现"1 次主调用 + 1 次评分调用"两段式）+ 结构化输出校验；
  - 前端：输入页 + 报告页（总分、雷达图、问题对照卡片）+ 3 个演示剧本按钮；
  - 数据：首批 30 条案例库（每场景 6 条）+ 提示词模板初版。
- **验收标准**：
  - 10 条测试文本全部返回合法结构化报告（字段齐全、分值 0–10、等级枚举正确）；
  - 单次分析耗时 ≤ 10 秒，成本 ≤ 0.05 元；
  - 雷达图、问题卡片正常渲染，演示剧本一键可用。

### 阶段 2：功能优化（建议 2–3 周）

- **目标**：提升专业性与稳定性，让"专业体检"名副其实。
- **完成内容**：
  - 案例库扩至 100 条（每场景 20 条），由指导教师审核质量；
  - 三条分析线并行 + 逐句问题定位；文化知识库完善（补充日韩/中东/欧美/东南亚典型文化画像）；
  - 评分校准：用 30 条盲测语料对比 AI 评分与专家评分，调权重与提示词；
  - 稳定性：失败重试、schema 强校验、provider 切换开关、Ollama 本地兜底跑通。
- **验收标准**：
  - 案例库 100 条全部通过导师质量审核；
  - 30 条盲测语料中，AI 总分与专家评分的误差 ≤ 10 分占比 ≥ 80%；
  - 接口失败率 < 5%（含人为构造的异常输入）。

### 阶段 3：比赛展示优化（建议 1–2 周）

- **目标**：让评委 3 分钟看懂价值、记住亮点。
- **完成内容**：
  - 3 个完整演示剧本（邮件催款 / 谈判压价 / 会议发言）打磨话术，演示时长控制在 3 分钟内；
  - UI 品牌化（CrossBridge 视觉、风险色系、加载动画、案例展示区）；
  - 预录演示视频（防现场网络/设备事故）+ README 宣传页 + 答辩 PPT 大纲与 Q&A 清单；
  - 现场环境预演：断网演练（Ollama 兜底）、备用设备、一键启动脚本。
- **验收标准**：
  - 3 分钟内完成"问题文本 → 报告 → 亮点讲解"完整演示；
  - 断网/无 Key 情况下仍可完成演示（本地模型或预录视频）；
  - 评委 5 个高频问题（与翻译工具有何区别？专业壁垒在哪？AI 出错怎么办？）均有 30 秒标准答案。

## 十、风险分析

| # | 风险 | 影响 | 解决方案 |
|---|---|---|---|
| 1 | **AI 输出不稳定**（评分忽高忽低、字段不合法、回答发散） | 报告不可信，演示翻车 | 全部结构化 JSON 输出 + 后端 schema 强校验 + 非法重试 1 次 + 规则兜底；六步拆小任务，单步失败不影响整体；评分锚点写死进提示词，减少自由发挥 |
| 2 | **缺少专业特色**（评委觉得"不就是套壳 ChatGPT 吗"） | 被归为普通 AI 工具 | 三件"专业内核"必须做扎实并可视化：五维评价模型（报告页直接展示）、100 条专家案例库（报告附案例对照）、跨文化理论框架（问题解释中引用"高语境""面子理论"等专业术语并通俗化解释）；答辩强调"标准来自学科，AI 只是执行" |
| 3 | **Demo 过于普通**（输入框+文本框，无记忆点） | 淹没在海量 AI 项目中 | 视觉记忆点：风险雷达图 + 绿黄橙红风险徽章 + "原文→问题→优化"对照卡片 + 案例对照区；流程记忆点：分步分析动画；内容记忆点：演示剧本有"外贸新人差点丢单"的故事感 |
| 4 | **与普通翻译工具区别不足**（评委第一反应"这不就是个翻译"） | 定位被误读 | 产品层：报告输出的是"风险分析"而非译文，UI 不主打译句而是主打问题卡片与评分；话术层：一句话切割定位——"翻译告诉你这句话怎么说，我们告诉你这句话**什么时候不该这么说、为什么、怎么说更好**"；演示时故意选一句"翻译完全正确但文化上很危险"的句子（如直译 "We don't need your products"）制造对比冲击 |
| 5 | **比赛展示效果不足**（现场网络差、紧张忘词、设备故障） | 准备白费 | 三层兜底：演示剧本一键填入（不靠临场打字）、预录演示视频（防一切现场事故）、Ollama 本地模型（断网可用）；提前 3 次全流程彩排 + 备用笔记本；答辩 Q&A 清单提前写好 |

**额外风险提示**：比赛现场若使用他人电脑演示，需注意 API Key 安全（不进前端、用完即撤）；若使用公共网络，优先本地模型或预录视频。

## 附：开源项目调研结论（无侵权风险清单）

> 按您的要求，优先调研了 GitHub 上可直接使用、无侵权风险的开源项目。结论如下。

### A. 可直接采用（许可证允许商用/比赛使用，无侵权风险）

| 项目 | 用途 | 许可证 | 说明 |
|---|---|---|---|
| [Ollama](https://github.com/ollama/ollama) | 本地部署 LLM（离线兜底） | **MIT** | 本地跑 Qwen3 等小模型，完全免费、断网可用 |
| Qwen3 系列模型（通义千问） | 开源 LLM 底座 | **Apache 2.0**（Qwen3 多数版本） | 可免费商用，中文能力强，可在硅基流动/Ollama 上调用 |
| DeepSeek 模型与 API | 主用分析模型 | 开源权重 + 官方 API 极低价 | `deepseek-chat` 约 1–2 元/百万 tokens，单次分析不到 1 分钱，比赛成本可忽略 |
| [硅基流动 SiliconFlow](https://siliconflow.cn) | 免费模型 API | 平台服务（注册赠免费额度） | 可免费调用 Qwen2.5-7B 等开源模型，接口与 OpenAI 兼容 |
| [FastAPI](https://github.com/fastapi/fastapi) | 后端框架 | **MIT** | 类型安全、自动文档，适合快速开发 |
| Vue 3 / Vite / Element Plus | 前端技术栈 | **MIT** | 国内资料多、上手快 |
| Apache ECharts | 雷达图等可视化 | **Apache 2.0** | 报告页核心图表 |
| SQLite | 数据库 | **公有领域** | 零配置 |
| openai Python SDK / requests | API 调用 | **MIT / Apache 2.0** | 标准库级依赖 |

### B. 同赛道情况：没有可直接复用的"跨文化风险检测"开源项目

- 调研发现最接近的是 [smart-trade-ai](https://github.com/chefroger/smart-trade-ai)（外贸业务员 AI 助手，含邮件/合规等 B2B 技能）等外贸类项目，但它们的定位是**获客/外贸流程助手**，与本项目"**沟通风险检测 + 五维评价 + 文化解释**"的定位不同，**且任何第三方仓库代码都不能直接复制进自己的项目**（需逐一核对许可证，超出本项目需求）。
- **结论：本项目的核心逻辑（评价模型 + 案例库 + 分析流程）需要自研——这恰恰是比赛的创新点与加分项**，也正好发挥商务英语专业的学科优势。

### C. 合规使用三条铁律（比赛答辩可能被问）

1. **保留许可声明**：使用开源库时保留其 LICENSE/版权声明（Vue、FastAPI 等 MIT 项目需在源码中保留版权头）。
2. **模型遵守各自协议**：Qwen 用 Apache 2.0 版本；若换用其他模型先查其许可证；本项目自研的提示词、案例库、评价模型属于团队原创，可自由使用。
3. **数据合规**：案例库素材来自自建与文献改编，标注来源；演示不输入真实客户隐私数据。
